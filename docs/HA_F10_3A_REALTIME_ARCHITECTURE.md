# F10.3A - Luma Realtime and resync architecture gate

**Date:** 2026-10-09
**Baseline:** `1b0748256f51b7832caa03eed30822ea8d0690b9` (`main == origin/main`; tracked tree clean)
**Verdict:** **B - CORE PREREQUISITE REQUIRED.** The Core transport hardcodes an 18-byte provisional binary StreamStart. A reusable Core change must produce the public TEXT JSON marker and give its work item enough storage before Luma can expose the selected public v1 wire. A product-selectable API minor version is also required so Luma can advertise 1.1 without claiming that Hydro and Doser have this product feature. This gate changes documentation only.

## Authority and CURRENT audit

Phase 9 is CLOSED. Phase 10 is IN PROGRESS. F10.1A is CLOSED, F10.1B and F10.2 are CLOSED/CURRENT, and F10.3 is REQUIRED NEXT. Luma HA has 13 read-only polling sensors. Luma commands and product WS are not CURRENT; SEC-101 is OPEN.

Core has `RealtimeStreamSequence` (nonzero `uint64_t`, no wrap), `RealtimeStreamPosition` (`BeforeFirst` or `AtSequence`, with sequence zero invalid), a per-runtime `RealtimeStreamSequencer`, and nonzero `RuntimeIdentity` with a 16-uppercase-hex formatter. `RealtimeNotificationMetadata` couples runtime and issued sequence. `RealtimeSnapshot<T>` couples a copied typed payload, runtime, position and `CoherentCurrent` state. `RealtimeCohortPublisher` invalidates/builds/publishes a finite resource set at one position, publishes the StreamStart state, then submits a notification; `republishCurrentCohort()` repairs/restamps without issuing a new position. These are transport-neutral CURRENT capabilities, not a Luma server composition.

`EspIdfWebTransport` owns the single HTTPD listener, optional same-port WS route, seven-slot client registry with fd generations and CONNECTING/LIVE/CLOSING states, a four-slot notification work pool with 256-byte payloads, a separate per-client StreamStart work item, sticky recovery, generation-gated fanout, and `serviceRealtimeRecovery()`/`tryClearRealtimeRecovery()`. `Busy`, `QueueWorkFailure`, cohort failure and per-fd send failure have distinct paths. `Accepted` means queued work, not client delivery. These capacities are **CURRENT implementation capacities**, not public protocol limits. The [F9.6C classic ESP32 HIL](WEB_REALTIME_F9_6C_HIL.md) physically proved same-port HTTP/WS, ordering, reconnect, runtime change, real four-slot saturation, slow-client recovery and HTTP progress in an isolated fixture. It did not prove a Luma endpoint or public frame schema.

The transport currently encodes StreamStart internally as binary: byte 0 is `1`, bytes 1-8 are little-endian runtime value, byte 9 is `1` for BeforeFirst or `2` for AtSequence, and bytes 10-17 are little-endian sequence (zero only as the BeforeFirst placeholder). Its source explicitly calls this provisional F9.6B marker, not the final RT-101 wire. The F9.6 HIL fixture also creates its own binary notification payload; `publishRealtime(metadata, type, payload, length)` copies those bytes unchanged. The transport does **not** serialize notification metadata into the payload. Neither binary layout is public v1, and neither may be inferred as a product contract from HIL.

Production Luma's `setup()` samples Core and Luma projections before `NativeWebService.begin()`. `loop()` runs `FirmwareApp::update()`, network/NTP, one queued Web action, then Core and Luma publication. The loop/Application context is the only mutable-state reader/writer for the status projection; HTTPD callbacks only read `PublishedSnapshot<LumaStatusProjection>`. Luma has one `EspIdfWebTransport`/`NativeWebService` on port 80 and no `setRealtimeEndpoint`, sequencer, runtime identity state or recovery supervisor. The Core `Esp32RuntimeIdentityGenerator` and `RuntimeIdentityState` exist, but Luma does not compose them. The generator needs its checked exclusive entropy window before ADC, I2S, Wi-Fi or Bluetooth use; no DeviceId/MAC fallback is legal.

F10.2 HA currently reads `/api/system` and then `/api/lumasense/status` every 10 seconds through one coordinator. The 13 sensors use mode, active profile (and profile-name attribute), day state, time validity, overall health, and eight final levels. `LumaStatus.from_json` and `SystemInfo.from_json` validate required keys but ignore unknown extra keys. Thus an additive `realtime` status object is compatible with the existing polling client; the JSON size bound remains 65536 bytes. Entity unique IDs and Device Registry identifiers derive from stable `device_type:device_id`, not runtime identity.

## Public route, version and exact v1 wire

Use exactly **`/ws/realtime`** on the same HTTPD handle and configured HTTP port. It is a common transport route; the product supplies kind and projection semantics. `/ws` is too generic, `/api/realtime` suggests HTTP request/response, and `/api/lumasense/realtime` unnecessarily makes a common wire product-specific. The path is shorter than the transport's 63-character path capacity and collides with neither Core reserved GET paths (`/`, `/assets/aqua.css`, `/api/system`, `/api/diagnostics`) nor Luma's registered GET/POST routes. Call `setRealtimeEndpoint("/ws/realtime")` before `NativeWebService.begin()`; register product HTTP routes before begin as today. A registration failure fails the optional Web start; it never blocks autonomous lighting.

The public v1 frames are **WebSocket TEXT containing UTF-8 JSON objects**, compactly serialized by the server. One JSON object occupies one complete WS message. Binary frames are invalid. JSON makes the HA Python client and standard WS tools simple, and the bounded frames below fit the current 256-byte notification capacity. The external compatibility axis is the existing `api_protocol_version`, not a second Realtime version. A Luma device offering this contract reports `{ "major": 1, "minor": 1 }` in `/api/system`; 1.0 remains the polling contract. A 1.x client ignores unknown optional fields but validates all required v1 fields and types. Unknown major is unsupported. A HA client attempts `/ws/realtime` only for verified Luma API >= 1.1; failure falls back to F10.2 polling. Hydro/Doser remain at their actual advertised version until their own reviewed cutovers. The reusable Core version source therefore needs a per-product supplied minor instead of changing one global 1.0 constant for every product.

Exact required frame schemas (no `payload` or other control frame in v1):

```json
{"type":"stream_start","runtime_id":"0123456789ABCDEF","position":{"kind":"before_first"}}
{"type":"stream_start","runtime_id":"0123456789ABCDEF","position":{"kind":"at","sequence":"1"}}
{"type":"notification","runtime_id":"0123456789ABCDEF","sequence":"1","kind":"luma_status_changed"}
```

`runtime_id` is exactly 16 uppercase hexadecimal digits, representing a valid nonzero `RuntimeIdentity`; it changes with a firmware runtime and is neither DeviceId, MAC nor security principal. `sequence` is the canonical base-10 string form of an integer from 1 through 18446744073709551615: no sign, whitespace or leading zero. Decimal strings preserve all 64 bits in Python, JavaScript and debugging tools. `position.kind` is exactly `before_first` or `at`; `before_first` has no `sequence` member, and `at` has the required string `sequence`. A Notification always has a numbered sequence; the only v1 kind is `luma_status_changed`. The frame has no state payload: it invalidates the client's view and requests an authoritative HTTP refresh. Field order is not significant to parsers. Producers emit the compact representation used in the size budget. Future additive keys under API 1.x may be ignored, while missing/wrong required keys are invalid.

The transport must encode the public StreamStart as TEXT rather than its provisional binary marker. The Luma Application/Web notification callback must serialize `RealtimeNotificationMetadata` plus the kind into the complete TEXT JSON frame; the transport only copies and sends that frame. It must verify that the serialized runtime and sequence equal the metadata passed to `publishRealtime`. No Luma semantic kind or payload formatter belongs in the Core transport.

### Frame size budget

The conservative upper bound uses the longest valid runtime string (always 16 bytes), a 20-digit maximum sequence, exact ASCII field names, braces/quotes/commas and compact JSON with no optional fields. These are UTF-8 byte counts, not estimates:

| Complete serialized object | Maximum bytes | Margin under current 256-byte payload |
| --- | ---: | ---: |
| StreamStart `before_first` | 90 | 166 |
| StreamStart `at` | 114 | 142 |
| Luma Notification | 118 | 138 |
| Status-body `realtime` object alone, `at` | 105 | N/A: HTTP body, not WS work payload |

No application control or heartbeat frame is selected, so its v1 budget is zero. The Core StreamStart work storage is currently 18 bytes and **must be enlarged to at least 114 bytes** (a bounded 128-byte slot is sufficient) while switching its WS opcode to TEXT. The 4 x 256-byte work pool and seven client slots remain implementation capacities; the full HTTP status body is streamed by the HTTP response writer and is not subject to the WS 256-byte capacity. No protocol-wide 256-byte limit is declared.

## Luma cohort, status metadata and transition rule

The finite F10.3 full-resync cohort has **one resource: `GET /api/lumasense/status`**. It is the authoritative changing Luma entity projection. The existing URL, field names, types and meanings stay intact. Its response gains this optional API 1.1 top-level member, copied atomically with the status payload:

```json
"realtime":{"runtime_id":"0123456789ABCDEF","position":{"kind":"before_first"}}
"realtime":{"runtime_id":"0123456789ABCDEF","position":{"kind":"at","sequence":"1"}}
```

The snippets above are exact top-level `realtime` member fragments, not standalone JSON documents. The HTTP handler takes one immutable published copy and writes the payload and metadata from that copy; it returns 503 if the status projection itself is unavailable. With WS unavailable for this runtime, it serves the existing status payload without `realtime`, preserving F10.2 polling. A connected F10.3 client treats missing/invalid metadata as resync failure and uses polling. The wrapper is `RealtimeSnapshot<LumaStatusProjection>` or an equivalent single copied value with a validated optional Realtime marker and a plain-status fallback. HTTPD never reads mutable `FirmwareApp`, network or diagnostics state. The Application loop owns candidate construction and publication. Publication/build failure after a sequence is issued invalidates the cohort, withholds that notification and requests recovery.

`GET /api/system` is **outside** the Realtime cohort. `device_type`, `device_id`, API version, firmware/hardware and Core version are stable identity/compatibility data for a firmware runtime; `uptimeMs` changes continuously and `restartReason` is runtime metadata. Adding `/api/system` would impose restamping or false stream transitions without helping the 13 Luma entities. HA still fetches it first on setup, every full resync/reconnect and every fallback/safety refresh. It validates the configured stable `device_type:device_id` and API version before accepting the status; it never compares a system watermark. The status `runtime_id` binds the changing snapshot to WS. A Luma reboot keeps the same ConfigEntry, Device and entity unique IDs, but creates a fresh runtime ID and a new BeforeFirst stream.

The v1 `luma_status_changed` fingerprint is the canonical, serialized-value projection of: `mode`, `activeProfile`, `activeProfileName`, `dayState`, eight `requestedLevels`, eight `finalLevels`, `globalPowerLimit`, `timeValid`, `wifi.state`, `wifi.connected`, `wifi.ip`, and `overallHealth`. Float comparisons use the existing status wire precision (two decimals), avoiding sequences for invisible sub-cent changes. The Application side compares the new fingerprint to the last successfully published fingerprint. Each distinct net state at a bounded presentation turn issues one sequence and publishes a full coherent status snapshot before notifying; multiple loop updates before that turn coalesce into one state. If a value changes and reverts before the turn, no externally visible transition remains. The scheduling interval is a measured implementation parameter for F10.3B HIL, not a public wire guarantee; publication must never send on every loop iteration.

Ordinary `localTime` second ticks and `wifi.rssi` jitter are explicitly **outside** v1 stream continuity and do not issue a sequence. The `realtime.position` watermark covers the declared fingerprint above; it does not claim that these incidental status fields are frozen. They remain readable from current HTTP status and may be republished at the same watermark by the serialized Application owner. A wall-clock correction without a change to `dayState` or `timeValid` likewise causes no v1 notification. F10.3's 13 entities do not consume those incidental fields. A later client needing notifications for them requires a reviewed kind/contract. The one-resource cohort can be restamped at its current position for incidental updates without issuing a new sequence; an unsuccessful restamp invalidates currentness and uses the normal recovery path.

Before accepting WS clients, the composition owner must: generate one nonzero fresh runtime identity in the checked early entropy window; construct the sequencer; publish a complete Luma baseline with `BeforeFirst`; publish matching StreamStart state; register HTTP/WS routes; then begin the one HTTPD listener. On identity or Realtime baseline failure, do not expose the WS endpoint for that runtime; continue autonomous lighting and publish the ordinary read-only HTTP status for F10.2. Do not synthesize runtime identity from DeviceId or MAC. If the Luma status itself cannot be built, HTTP returns 503 until a valid Application-side publication succeeds.

## HA connect, refresh and fallback

Keep one WS client task beneath the existing `LumaCoordinator`; the 13 `SensorEntity` classes, config entry/device identifiers and unique IDs remain unchanged. Setup verifies `/api/system` and uses the existing polling coordinator. For an API >= 1.1 Luma with a reachable WS route:

1. Connect, require a valid `stream_start` as the first frame and capture runtime/position S. Start a bounded overlap buffer before HTTP fetch.
2. Fetch `/api/system`, verify stable configured identity and compatible API; then fetch the sole cohort resource `/api/lumasense/status`. Parse both with the existing typed models plus the new metadata validator.
3. Require coherent status metadata with the same runtime as S and position N >= S. Install the typed status at N; discard buffered notifications <= N.
4. Validate the remaining buffered notifications as contiguous N+1, N+2, ... . They are refresh hints, not state patches. Queue one `LumaCoordinator.async_request_refresh()` if any are newer than N.
5. While live, track `seen_position` separately from `installed_watermark`. One coordinator refresh may be in flight and one dirty flag pending; consecutive notifications coalesce into that bounded work. Each successful HTTP refresh verifies `/api/system` and the status runtime/watermark, then installs the full typed snapshot. If new hints arrived during the GET, schedule one more `async_request_refresh()`. No notification modifies an entity locally.

The overlap buffer bounds both notification count and total bytes; the connection/resync loop also bounds consecutive attempts and backs off before retry. F10.3C measures numerical limits; they are not public protocol fields. Overflow, forward gap, failed coherence check, new runtime, disconnect, malformed frame, unsupported shape or repeated resync failure discards overlap and starts a full WS-first resync or enters polling fallback. Do not combine mixed watermarks. Duplicate/old sequences <= installed N are ignored; sequence zero is invalid. An unknown kind triggers full HTTP resync because its meaning cannot safely be discarded. Unknown message type or binary frame closes this WS session and falls back to polling until a later bounded retry. No sequence or runtime state is persisted in HA storage.

WS failure never makes the Luma entities unavailable by itself. Fallback retains F10.2's 10-second coordinator polling and its normal unavailable/recovery behavior. When WS is healthy, replace the unconditional 10-second loop with notification-triggered refresh plus a **slower safety poll**, whose interval is measured in F10.3C. The safety poll catches silent WS stalls, validates identity/status and updates fields outside stream continuity. Reconnect, integration reload, HA restart, Luma reboot, Wi-Fi reconnect and HTTPD recycle all start with a new StreamStart and full HTTP resync. Luma reboot changes runtime identity while preserving physical DeviceId, the same config entry, Device and all 13 entity unique IDs.

No application heartbeat is required for F10.3. The present HTTPD WS callback consumes and rejects inbound frames, so a client must not assume protocol ping/pong is usable without a separate test or Core support. The slower safety poll and 10-second fallback supply bounded state refresh while the silent-blackhole behavior is measured later. This does not assert that a TCP connection is healthy merely because it remains open.

## Recovery, lifecycle and security

After any issued N, a failed status build/publication, `Busy`, `QueueWorkFailure`, `RecoveryRequired`, invalid metadata or another pre-acceptance notification failure cannot be ignored. Request sticky recovery, suppress fanout, close affected WS clients and republish the complete current cohort at the already-issued current position before clear. A send failure for one fd closes that connection; it need not invalidate other live clients. The Application loop must call bounded `serviceRealtimeRecovery()` even when no further Luma transition occurs. Clear only after old clients are gone, the server is ready, and the published StreamStart state and coherent cohort match the current runtime/position. No failure here automatically changes lighting Safety or Health.

The Luma composition root owns the transport and borrowed callbacks. A product Web lifecycle supervisor must handle sustained `RetryNeeded` or `TransportRecycleSuggested`: call `webTransport.tryStop()` from the Application owner, outside HTTPD callbacks and without holding its mutex; retry failed stop without destroying any borrowed route/page/action context; only after successful stop republish the cohort/StreamStart state and call `nativeWebService.begin()` on the same route table/port. If stop cannot complete, keep contexts alive and report optional Web failure while lighting continues. `NativeWebService::begin()` can restart a previously stopped transport with its registered routes; never call its aborting `stop()` as a speculative recycle step. This is a **Luma product lifecycle implementation**, not a missing Core stop primitive. Tests must prove restart and callback lifetimes.

**SEC-101 is NONBLOCKING for this scoped read-only F10.3.** Luma's current `/api/system` and status reads are public on the local listener. The selected WS frame carries only runtime/sequence and a status-change hint, no commands, state values or credentials; its exposure is no broader in data content than the current public GET surface. The route remains local-network deployment policy, not a general claim that LAN is trusted. The full Auth/session architecture and any command authority remain SEC-101 OPEN and require a separate gate; no credentials are invented here.
