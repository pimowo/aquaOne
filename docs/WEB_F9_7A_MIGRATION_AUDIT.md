**Status:** design/audit gate, documentation only. Baseline `a0b6c3f0fb00bd2affa0aea214bbb16f344bd51c` (`main == origin/main`). F9.6 is closed. This document maps the code at that baseline; it does not authorize a production switch or define a final wire schema. F9.1, F9.2–F9.6 and the coherent resync rules of F9.6A remain authoritative. ## 4. Target Application boundaries

**Reads.** Application samples each authority after its owner updates it, builds a trivially copyable bounded projection with owned strings, wraps it in `RealtimeSnapshot<T>` and publishes via `PublishedSnapshot<T>`. HTTPD copies the entire wrapper, checks availability/coherence and serializes after releasing the synchronizer. It does not hold a mutable `FirmwareApp`, controller, config owner, runtime coordinator or diagnostics service reference. Core `SystemProjection` takes identity, uptime and restart reason from existing system providers; `DiagnosticsProjection` takes existing `DiagnosticsService` / Phase 6 typed providers and Health aggregation. These are read models, not new authorities. Luma status combines `FirmwareApp` state/config/local time with Network and Diagnostics samples. Hydro status comes from `HydroSenseApp::updateStatus()` / `SystemStatus`; Hydro dynamic pages additionally need config-visible, storage, network and system projections. The existing `/settings` page currently renders Wi-Fi password fields; the migrated GET projection and any resync resource must **never** return SSID passwords, AP passwords or other credentials. SSID itself is not a credential, but its visibility remains an Auth/policy decision. Blank password inputs and save semantics require an explicit UI/config decision before cutover.

**Domain actions.** HTTPD performs bounded parse and syntax validation, then submits pointer-free typed requests to an Application-owned bridge. Application applies auth/policy, Maintenance/Safety/Action Lock gate and `CommandPipeline` or a deliberate product Application handler, then returns a bounded semantic result. Luma existing `FirmwareApp` methods are **Application entry points**, not evidence that Core `CommandPipeline` is already wired for Luma; migration must wrap them in a serialized command path. Luma profile selection is a Config action because its current method validates and persists `DeviceConfig`; keep that persistence inside the Application-owned workflow. Hydro controller methods are similarly existing effectors, not an existing typed command handler. `service_toggle` is state dependent and must be resolved in Application, rather than based on a stale HTTPD read.

**Hydro Config.** `/api/settings` currently copies `config_`, calls `HydroSenseConfigStorage::save`, assigns `config_` and asks for restart inside a Web handler. The target is HTTP parse → owned bounded config request → serialized Application config owner → build candidate from current config → validate → persist with failure/verification result → commit active state/apply or mark restart required → semantic HTTP result. `ConfigLifecycle.h` supplies typed operations/callback boundaries; a Hydro composition adapter and exact save/apply/restart wiring do not yet exist. This is an implementation blocker for that route, not a blocker for accepting this audit or permission to mutate Config/storage in HTTPD. Preserve atomic save and failure behavior from CFG-101. The form contains SSID, Wi-Fi password and AP password: do not log credentials, copy them into bounded owned storage only, and never return passwords in the migrated settings GET or WS stream.

**Restart.** Doser currently sends 202 and `WebManager::loop()` later calls `stopPumps()` then `DoserWebRuntime::restartDevice()` → `ESP.restart()`. SYS-107 is an **accepted target contract, not an implemented `RestartRequester` class** at this HEAD. F9.7E therefore must provide the minimal system owner/requester/executor composition needed by SYS-107 or wait for that implementation: authorized bounded request → Application system/recovery workflow → pending USER_REQUEST → pump-safe point → platform executor. Send `OperationStarted`/202 only after acceptance; HTTPD never calls `ESP.restart()`. OTA success uses OTA_COMPLETE only after verified completion. No parallel restart framework.

**OTA decision: C.** Doser's full production switch is blocked until `/update` POST has a safe native replacement. Keeping an Arduino WebServer just for OTA would violate one physical owner on the product; dropping OTA would remove a shipped admin function. A Doser-owned writer adapter (no Core OTA framework) is a possible F9.7F implementation, subject to separate review and hardware test; common OTA policy remains Phase 11 / MNT-102. The current chunk callback also calls `DoserWebRuntime::serviceDuringUpload()`, which runs driver, Wi-Fi, time, scheduler, diagnostics and MQTT loops; it cannot be carried into HTTPD. The HTTPD side must authenticate before accepting firmware bytes, parse multipart and validate declared/actual size against partition capacity, own each bounded chunk until consumed by a serialized authorized Maintenance/system workflow, apply backpressure without unbounded allocation, call a product `Update` writer outside HTTPD, and guarantee abort on malformed input, disconnect, timeout, write/end failure and stop. Complete only after final verification, release OTA/Maintenance state on every terminal path, then request delayed safe-point restart. Existing Doser `setOtaInProgress` is scheduler-local behavior, not proof of Core Maintenance transition. Never pass HTTPD buffers or request pointers to Application. The upload chunk contract is separate from normal POST body copies.

## 5. Body, HTTP result and compatibility policy

Normal GET and bodyless POST may use existing dispatch. For normal action POST, add per-route `Content-Type` and `Content-Length` validation, bounded receive with timeout/short-read handling, and either parse entirely on HTTPD into an owned typed value or copy a bounded NUL-terminated buffer into an owned request; no borrowed pointer crosses the bridge. Accept Hydro's existing `text/plain;charset=UTF-8` for both form-encoded bodies at cutover; any new media type is additive. Reject malformed/empty body as 400, unsupported media as 415, oversize as 413, I/O failure as a bounded 4xx/5xx transport error and close/drain unread bytes. Current native transport rejects all nonempty bodies, so no product POST is migration-ready. **Every** migrated normal POST must have a finite per-route cap before it can start; measurement does not permit an interim unbounded body. Proposed initial capacities to **verify against real form/browser samples and heap on target boards**: Luma routes 512 B (existing `MAX_CONTROL_BODY`); Hydro `/api/control` 128 B for one action token; Hydro `/api/settings` at least 2048 B for 20+ URL-encoded fields and escaped credentials, with a measured finite per-route cap required before implementation; Doser `/api/restart` 0 B. A single global 256 B limit is invalid. For settings, decoded field capacities and total URL-encoded length must be separately bounded. Multipart `/update` uses a streaming state machine and firmware-size/partition limits, never a 2048 B request copy.

| Outcome | Required HTTP behavior | Contract state |
| --- | --- | --- |
| Parse/auth/policy rejection before acceptance | 400/401/403/409 as applicable; no effect | Existing product body/error vocabulary varies; WEB-102 mapping open. |
| Bridge `QueueFull` / pre-acceptance synchronization failure | 503 (or separately agreed 429), explicit no acceptance; bounded response | Status choice beyond no-acceptance remains WEB-102 OPEN. |
| Accepted + Completed/Applied or NoChange | 2xx with existing route-specific result when possible | Luma currently JSON `ok/result`; Hydro plain `OK`; preserve initially. |
| Accepted + semantic rejection | 4xx/5xx according to typed result, never silently 200 | Luma 400/409 current; Hydro 400; final machine codes WEB-102 OPEN. |
| Accepted + timeout | Explicit outcome unknown, e.g. 202 plus `outcome_unknown` or 504 with same warning; never claim cancellation | Exact status/schema WEB-102 OPEN; client must resync/read before acting again. |
| OperationStarted | 202 only after operation accepted; no implied completion | Existing Doser restart 202; OTA completion is separate. |

`CMD-102` idempotency/deduplication is open. Client retry after an accepted timeout can repeat non-idempotent effects (notably Hydro `service_toggle`, reset/mute or restart intent). Do not invent request IDs in F9.7. UI should disable duplicate submission and refresh authoritative state, but this does not solve exactly-once delivery.

Compatibility priority for every listed route is **MUST PRESERVE path and method** at initial product cutover. Normal request bodies are **MUST PRESERVE** for Luma JSON, Hydro form and Doser multipart/size header; bodyless reads/restart are unchanged. Current success response body/media type and successful status are **MUST PRESERVE** initially for Luma status/actions, Hydro status/control/settings, Doser restart/update, Core system/diagnostics and CSS/pages, since shipped JS depends on them. Internal error wording and transport-failure status are **MAY CHANGE** after route tests; final error envelope, Auth response, timeout code, settings secret display, diagnostics availability change and WS wire binding are **DECISION REQUIRED** under WEB-101/102/SEC-101. 404 path/status/plain body should be preserved unless explicitly reviewed. Suggested sets below are **composition proposals**, not a final JSON envelope. ## 9. TOOLCHAIN-2 audit

All six product environments currently say unpinned `platform = espressif32`, `framework = arduino`; Core pins the pioarduino 53.03.13 release asset for `esp32dev`. Source declarations alone do **not** prove product compatibility with Arduino-ESP32 3.1.3 / IDF 5.3.2. TOOLCHAIN-2 should pin the same platform release per product, preserve board and flags, compile each, then run board-specific HIL before release. Do not substitute Core's `esp32dev` board for an S3 product. No PlatformIO files are changed by F9.7A.

`aquaOneCore/README.md` Integration Guide still shows generic `platform = espressif32` for an example `esp32-s3` environment. It is not the pinned production Core environment; TOOLCHAIN-2 should update/annotate that example when product pins are implemented, so it does not appear to recommend the old unpinned baseline.

## 10. Tests, HIL, order and gates

Existing tests: Core `test_web` covers legacy `WebService` registration, built-ins, pages, auth/upload contracts through a mock `WebBackend` and should remain as legacy regression until retirement; it is not native HTTPD proof. Core `test_idf_web_transport`, `test_web_snapshot_foundation`, `test_web_action_bridge`, `test_web_realtime_foundation`, `test_web_realtime_resync_foundation`, and `test_web_realtime_resync_hil` cover foundation behavior, including classic ESP32 HIL, not migrated product routes. Hydro has no Web tests (`test/README` only). Doser `test_web_bridge` includes `WebManager.cpp` with fake backend/runtime and tests Basic Auth, delayed restart, streaming start/chunk/end/abort and failure cleanup; preserve behavioral requirements, rewrite transport-specific harness after cutover. New native tests need route registration/freeze/capacity, per-route body/framing/oversize/media handling, owned bridge lifetime and timeout races, exact compatibility JSON/text, projection availability/coherence, auth denial before side effects, ERROR/MAINTENANCE gates, config save failure/restart semantics, restart safe point, OTA disconnect/abort/backpressure, and no duplicate listener. Do not run these in F9.7A.

Recommended split, each reviewable and bisectable: **F9.7B** Core native route adapters, built-in projections, optional WebStartup/WebHealth and Application tick boundary; **F9.7C** normal bounded POST body and HTTP result mapping with native tests; **F9.7D** Luma migration plus TOOLCHAIN-2 Luma, semantic/native tests, compile and real board HIL; **F9.7E** Hydro migration plus Config boundary, TOOLCHAIN-2 Hydro, new native/product tests, compile and S3 HIL; **F9.7F** Doser normal/system route adapters and SYS-107 restart plus TOOLCHAIN-2 Doser, retaining the legacy server as sole production owner until all routes are ready; **F9.7G** Doser-owned OTA streaming adapter and atomic single-server cutover with separate S3 OTA HIL, or explicit Phase 11 deferral of the **whole Doser switch**; **F9.7H** cross-product review, remaining Gas/Fauna/Clima TOOLCHAIN-2 pins and board-specific proof when those projects are buildable. Do not ship partial Doser with two listeners or remove `/update` silently.

Proof per gate: F9.7B needs native tests for built-in snapshot routes, unavailable projections, WebHealth/startup and no transport poll; F9.7C needs bounded body/response, ownership, timeout and malformed/oversize tests. F9.7D preserves Luma UI JSON and 400/409/no_change, tests bridge and profile storage, ERROR/MAINTENANCE, then compiles and runs HIL on its real `esp32dev` hardware.
